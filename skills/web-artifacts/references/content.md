# 핵심 설계 내용 선정

## 코드에서 설명할 질문 추리기

먼저 요청 목적과 기존 자료에서 독자가 판단할 질문을 찾음. 모든 소스 파일을 도식으로 옮기기보다 요구사항을 지탱하는 설계 선택과 이해하기 어려운 경계를 우선함.

| 확인할 근거 | 화면에 담을 내용 |
| --- | --- |
| 실행 진입점, 설정, 외부 호출 | API·작업자·DB·외부 서비스의 실행 경계와 통신 |
| 스키마, 마이그레이션, 저장소 쿼리 | 실제 PK/FK·유니크 제약·주요 인덱스와 조회 목적 |
| 서비스, 트랜잭션 코드 | 대표 입력의 검증·변환·저장·응답, 실제 원자적 범위 |
| 상태 변경 조건, 오류 처리 | 정상 종료·취소·실패·만료·재시도 후 남는 데이터 |
| 잠금, 조건부 갱신, 중복 제약 | 경쟁하는 실행자가 무엇을 기다리고 누가 처리하는지 |
| 시간·금액·권한 등 도메인 계산 | 계산 기준과 경계 사례를 구체적인 값으로 설명 |
| 테스트, 측정 스크립트와 결과 | 입증된 동작·성능, 측정 조건, 아직 확인하지 않은 한계 |

자료와 코드가 다르면 차이를 표시하고 실제 구현을 추정으로 덮지 않음. 문서만 제공된 경우 코드로 확인한 것처럼 서술하지 않음. 파일 위치·함수명 등의 근거는 필요할 때 펼치는 상세 패널에 배치.

## 화면별 정보량

한 화면은 하나의 질문에 답하도록 구성. 도식에는 역할·흐름·조건·결과, 상세 패널에는 선택 요소의 책임과 설계 이유를 짧게 표시.

- 대표 입력 → 변환된 값 → 저장 상태 → 결과 중 그 설계를 이해하는 데 필요한 값 제시
- `왜 이 방식을 택했는지` 한 문장과 중요한 비용·한계 한 문장으로 시작
- 수치가 있으면 실제 배치 크기·시간·측정 조건을 확인. 설명을 단순화하려고 서로 다른 작업의 수치를 하나로 합치지 않음
- 현재 구현과 확장 제안은 명확히 구분. 큐·재시도·멱등성 보장을 코드에 없는데 있는 것처럼 그리지 않음
- 상태값을 성공으로 오해할 수 있으면 실제 의미를 설명. 예를 들어 외부 호출 전에 기록하는 상태는 외부 수신 성공을 증명하지 않음

## 어떤 화면을 우선 추가할 것인가

기본 후보는 전체 아키텍처 → 데이터 구조 → 주요 처리 흐름. 모든 프로젝트에 이 순서를 강제하지 않고 독자의 질문에 맞춰 조정.

보완 후보는 아래 세 기준으로 선택:

1. 핵심 요구사항인데 현재 자료에서 빠진 내용
2. 문장보다 그림으로 표현했을 때 이해가 크게 나아지는 내용
3. 기존 화면과 중복이 적은 내용

예를 들어 시간대를 다루는 프로젝트라면 시간대 계산을 먼저 보완할 수 있으나, 결제·재고 경쟁이 핵심이면 동시 처리가 먼저일 수 있음. 상태도·시간대·동시성 화면을 도메인과 무관하게 모두 생성하지 않음.
